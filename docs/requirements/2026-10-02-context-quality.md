# 知識與個人 Context 品質優化需求

日期：2026-10-02。依據：MAG 確認先寫需求文檔，再繼續執行優化。

## 目標與產品邊界

讓外部 Agent 取得與任務相關、仍然有效且有權讀取的知識和個人上下文。平台繼續管理身份、資料、審核與檢索；Agent 在外部執行。沿用 PostgreSQL 真源與私有 OpenViking，不替換現有引擎或引入另一套 Agent Runtime。

現有未提交的 Person＋Space、MCP 0.2.0 與 UI 修改保留。以下需求分階段交付，不能以第一階段測試通過宣稱 Wiki、雲端部署或外部 Agent 自主工作已完成。

## 問題與使用情境

1. 個人 Context 目前以完整查詢字串匹配標題／正文。「週報需附來源連結」無法可靠命中「MAG 對週報格式有哪些要求」。
2. 文件先佔用全部結果與字數，個人記憶可能完全被擠掉。
3. 個人目錄尚無向量索引；必須先處理索引版本、更新、刪除與模型變更，不能只增加相似度計算。
4. MCP 已有工具，但仍需證明跨進程調用會返回正確版本與來源，撤權後不可讀。
5. 跨文件結論缺少獨立治理單位；目前文件摘要不足以表達有效決策及衝突。

## 資料歸屬

- Person＋Space：使用者的 memories／skills／peers，以及明確授權的個人資料。
- Agent＋Subject：保留既有 Agent 對服務對象的專屬記憶，不自動搬移或複製。
- Knowledge Space：團隊共享文件；後續候選 Wiki 歸屬此層。
- sessions 維持明確接口讀取，不自動混入 Context；privacy 仍關閉。

## 第一階段：個人召回與上下文分配（本次實作）

### FR-01 授權內混合召回

個人 memories／skills／peers 採中英文詞項匹配與向量召回融合。中文採相鄰雙字詞項，英文／數字採詞項；只做正規化和分詞，不以硬編碼業務同義詞冒充語意模型。向量由既有 Embedding provider 提供，以配置的 endpoint＋model＋演算法版本作指紋，不包含密鑰。

只對已啟用且目前可存取的個人資料建立索引。背景 worker 每次處理一筆，長正文分段向量化；查詢只向量化問題，不在讀取請求內重算全部資料。舊資料由 worker 自動補索引。索引中／失敗仍可詞項檢索；回應明示 keyword／hybrid 與降級狀態。

### FR-02 版本與生命週期

索引必須與當前條目版本、模型指紋一致。修改／停用／刪除立即清除舊向量與租約；晚到結果不得覆寫新版或復活已刪資料。索引工作有持久租約、超時恢復與退避，最多自動嘗試三次；人工重試只重設索引，不改資料版本。網路 I/O 在資料庫交易外。

### FR-03 結果與字數預算

文件／舊 Subject 記憶為一組，個人 Context 為另一組。兩組均有可用結果時，先為個人資料保留 ceil(limit/3) 筆（最多 limit），以及約三分之一字數，再交錯補足空位；limit=1 時優先返回個人命中。未用名額與字數可被另一組使用。

三分之一為軟預算。若首輪沒有個人條目落在此預算內，但有一筆可在總 max_chars 中完整容納，先保留該筆，再分配文件，避免有效長記憶仍然被完全擠掉。

總筆數不得超過 limit，組裝 context 含引用標頭和分隔符的長度不得超過 max_chars。不截斷正文製造不完整規則；過長條目跳過並繼續找下一筆。排序必須穩定，不同通道的原始分數不直接相比。

### FR-04 權限及回應相容

保留 subject_id、space_ids 的既有契約：省略 space_ids 保留舊 Subject 路徑；明確指定只查指定空間；空陣列為空。不得擴張 Token Person、Tenant、Space、Agent 或目錄 grant。

模型／引擎查詢前限制資料範圍，返回前在政策鎖下重新檢查身份、權限、當前版本及狀態。所有個人結果保留 ID、版本、來源訊息、space_id 及參考資料標記。索引錯誤只返回固定代碼，不洩漏 provider 回應／密鑰。

### FR-05 可觀察性與可重試

條目回應附索引狀態／錯誤代碼；新增僅資料擁有人可用的索引重試接口。Context 附召回模式、降級原因及有索引／可讀條目數，限定於當前調用者有權訪問的資料。MCP 文檔解釋模式及預算；既有工具參數保持相容。

### 驗收

| ID | 情境 | 預期 |
|---|---|---|
| AC-01 | 中文改寫問句及英文多詞問句 | 不要求整句字面包含；語意無共同詞案例用可控向量測試及獨立真實模型驗證 |
| AC-02 | 文件填滿原 limit／max_chars | 合適的個人命中仍有保留位置；總量不超限 |
| AC-03 | pending／停用／刪除／未授權／另一 Person 或 Space | 個人結果不可見，亦不計入可讀統計 |
| AC-04 | 向量化途中改版、刪除、過期租約 | 晚到索引不能生效；新版可重新建立 |
| AC-05 | 查詢途中撤權或改版 | 返回前重查，不能返回已失效正文或以舊向量命中新版 |
| AC-06 | provider 失敗、無配置、模型切換 | keyword 降級；錯誤可辨識；舊模型向量不參與 |
| AC-07 | 超長條目、limit=1、空 space_ids、結果重複 | 有界、穩定、無重複，範圍不變 |
| AC-08 | 真正 Node MCP stdio → HTTP API | 可讀正確資料及引用；撤權後不能讀；不把協議測試算成 Agent 自主驗收 |

## 第二階段：持續個人化與外部 Agent 驗收

1. 個人偏好與背景由人明確標記為常駐，分配固定小預算；不把所有 memories 自動當偏好注入。
2. 被拒絕候選抑制重複提取，人工修正保護，新舊事實衝突提示，到期事項歸檔。
3. 選定真實外部 Agent 執行「提問→自主讀取→引用→使用者修正→再次讀取」；測量命中、上下文長度、費用和延遲。
4. 首批建立 30 個業務驗收問題，答案及來源由實際業務資料確認，不能用合成測試替代品質結論。

## 第三階段：跨文件候選 Wiki

同 Space 文件生成主題頁候選；每條結論保留來源文件／片段／版本。頁面區分目前有效決策、歷史決策、待確認事項與衝突；不自動把最近文件當最終決策。

生成更新時顯示差異，經人工審核才成為有效頁。來源更新／刪除／撤權後失效或標記待重審；閱讀仍按當前來源權限處理。驗收至少包含同名實體、舊新決策衝突、來源刪除、部分來源無權讀取及人工修正保護。

本階段需要獨立資料模型、背景任務和介面，不在第一階段順帶加入。

## 方案取捨

採用既有 Embedding 服務＋PostgreSQL 中有界個人向量資料，避免重建一套引擎身份映射；適合目前每目錄最多 1,000 筆、每次最多 10 個 Space 的內部規模。後续量測 CPU／資料量後可把候選召回移至受控向量索引，產品仍保有正文與授權真源。

暫不整體替换為 WeKnora，也不複製內置 Agent／沙箱。借鑒其知識整理、記憶生命週期及外部接入模式。
